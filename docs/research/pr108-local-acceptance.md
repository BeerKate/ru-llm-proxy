## Дополнительное исправление границ JSON

После основной сверки найден дополнительный случай замечания 1:
`Here's the payload: {"password":"Synthetic42","x":1}`. Апостроф перед JSON
мешал построить карту строк; контролируемый NER-хвост с лишними кавычкой и
запятой повреждал JSON. Похожий результат давали вводные незакрытые кавычки.

Сканер теперь пропускает апостроф внутри слова, продолжает поиск после
незакрытого фрагмента и может возобновить его с полного JSON объекта/массива,
проверенного стандартным decoder. Повторная интерпретация запрещена внутри
уже открытого контейнера и синтаксически корректного Python: строка `"{"`
не превращается в начало нового объекта. AST и JSON используются только
для разбора; исходный текст не исполняется и не пересериализуется.

Добавлены **52 теста** в уже выполняемый CI-файл `test_string_boundaries.py`.
На старой реализации первые 36 новых контролей дали 24 failed / 12 passed;
после исправления весь файл: **106 passed**.

Общая версия с исправлением: Analyzer **2315 passed / 1 прежний failed**
(глубина JSON 2000), guardrail + LiteLLM flow **1436 passed**,
статические **427 passed + 18 Make smoke checks**. Настоящий BERT через
Analyzer TestClient и функции маскирования/восстановления guardrail:
**36/36** полное строковое значение, корректный JSON и точное восстановление;
три префикса × три значения × ensure_ascii × обе политики Base64.
Проверка широких ошибочных NER-границ отдельно выполняется контролируемыми
тестами; настоящий BERT на этой матрице сам таких границ не выдавал.

Это исправление конкретного дефекта, не универсальный парсер повреждённого
кода или всех языков. Незавершённые внешние контейнеры, произвольные f-string
выражения и общая стратегия глубины JSON не объявляются решёнными.
Контейнерная приёмка полного маршрута остаётся необходимой.

## Воспроизведение

Запускать из чистой рабочей копии. В существующем Analyzer-окружении:

```sh
PYTHONPATH="$PWD/presidio:$PWD" python -m pytest -p no:cacheprovider -q presidio/tests --tb=short
make test-static PYTHON_LOCAL=python
python presidio/evaluation/pr108_acceptance.py \
  --checkout . --baseline c3151d8 \
  --model /absolute/path/to/verified/bert \
  --output /tmp/pr108-bert-comparison.json
```

Скрипт проверяет веса по manifest, экспортирует локальный baseline через
`git archive` во временную папку и последовательно запускает обе версии.
Клонирование/скачивание, изменение веток, отправка данных и запись исходных
payload не выполняются. В отчёте — версии, SHA256 шести наборов и модели,
агрегаты покрытия и отдельное время одного прохода. Временные данные удаляются.
Все шесть наборов входят в `presidio/evaluation/data/`; это известные регрессии,
не новая независимая выборка для оценки общего качества.

В отдельном guardrail-окружении с зависимостями проекта:

```sh
PYTHONPATH="$PWD/presidio:$PWD" LITELLM_LOCAL_MODEL_COST_MAP=True \
  python -m pytest -p no:cacheprovider -q litellm_guardrails/tests tests/e2e/test_guardrail_flow.py --tb=short
```

Для целевой среды остаются действующие команды CI:
`make test-recognizer-api`, `make test-hf-model-run`, `make test-ner-proxy`;
последний также с `PRESIDIO_ANALYZER_BASE64_POLICY=logistic`.
Требуются Docker и собранный закреплённый образ; в локальной проверке Docker
и Python 3.11 отсутствуют, поэтому эти команды здесь не запускались.

## Что ещё не подтверждено

- Контейнерный CI/Python 3.11 и полный запущенный LiteLLM → Analyzer → Redis →
  тестовый провайдер, обе политики, MASK/BLOCK, streaming и tool calls.
  Модульные/локальные проверки отдельных частей не заменяют этот запуск.
- Полнота всех сущностей, большие сравнения качества и стоимость на длинных
  историях. Старые результаты нельзя автоматически приписывать новой сборке.
- Общая стратегия подстановки маски в собственное числовое `contract_id`:
  прямая строковая маска нарушает JSON. Ревью явно отделяет этот вопрос от
  ошибочного маскирования соседнего timeout; соседний timeout исправлен.

Удалённые workflow исходного PR всё ещё `action_required`. Они не проверяли
локальные коммиты. Push и запрос повторного ревью выполняет пользователь;
одобрение запуска workflow из fork относится к сопровождающему проекта.
